## 기술 개요

### 실행 파일

`mgp_rel_umd.elf` 는 **암호화되어 있지 않습니다**. `.text` = VA `0x08804000` (2.9MB),
`.data` = VA `0x08ACDBDC` (434KB). 임포트에 `sceLibFont` 가 있어 PSP 시스템 폰트(PGF)를
쓰고, 동시에 자체 GIM 비트맵 폰트(`font10c.gim`, `flag_fonts`, `Lmsg.gim`)도 있습니다.
엔진은 소니 i3d (`.data` 의 `i3d_package_version 050121-stable-060426`).

`.data` 에서 찾은 일본어는 전부 엔진 디버그 메시지이고, **게임 텍스트는 `.xb` 안**에 있습니다.

### 리소스 시스템

`disc0:/PSP_GAME/USRDIR/xbdata/%s` 로 열고 `crs/%02d/hol%02d.xb`, `kuwa/pc/face/face%02d%s.xb`,
`yumo/loadmes/A%02d.xb` 같은 서식으로 참조합니다. `.xb` 안의 리소스 이름은 **개발 당시 경로**
(`..\data\hatsuyama\common\font10c.gim`)라서 무엇이 무엇인지 바로 읽힙니다.

### `.xb` 컨테이너

```
0x00  'x' 'e' 0x00 0x01
0x04  u32 count
0x08  count × { u32 dec_size, u32 flags_off }
        flags_off 상위 4비트 = 코덱 플래그(0·1·2·3)
        flags_off 하위 28비트 × 4 = **그 리소스의 청크 절대 오프셋**
+     u32 name_dec, u32 name_comp               name_comp==0 이면 이름표 무압축
+     [이름표]
+     리소스별 [ u32 dec, u32 comp ][스트림] … 청크 반복
```

2,806개 중 581개는 이름표가 무압축이라 리소스 목록을 바로 읽을 수 있습니다.

### 압축 코덱 (해독 완료)

청크 = `[u32 dec][u32 comp]` + 스트림이고 **comp 는 8바이트 헤더를 포함한 길이**입니다.
스트림 첫 바이트로 코덱이 갈립니다 — `(b & 3) == 0` 이면 LZ(사전이 비어 있어 반드시
리터럴 토큰으로 시작), 그 외는 허프만입니다. **허프만 출력이 다시 `[dec][comp]` + LZ
스트림인 2단 체인**이 흔해서, 엔트리의 최종 크기와 첫 청크 크기가 다릅니다.

알고리즘은 비암호화 실행 파일에서 그대로 옮겼습니다.

| 루틴 | VA | 내용 |
|---|---|---|
| LZ | `0x0882ADD4` | `(t&3)==0` → 리터럴 `(t>>2)+1`개 / `t&1` → 2바이트 매치 / else 3바이트 매치 |
| 허프만 | `0x0882ACE4` | 10비트 직접조회, 16비트씩 리필, 길이 ≥ 11 은 생 8비트 탈출 코드 |
| 표 생성 | `0x0882AC0C` | `u8 max_len` + 길이별 개수 + 심볼. **비트반전 코드로 색인** |

⚠ 길이·거리 추출이 **allegrex 전용 `ext` 명령**(`0x7ce61040` = `ext a2,a3,1,3`,
`0x7ce64880` = `ext a2,a3,2,10`)이라 일반 MIPS 디스어셈블러로는 `.word` 로만 보입니다.
이걸 읽지 못하면 비트폭을 맞출 수 없습니다 — 손 해독이 계속 모순에 빠진 이유였습니다.

검증: `dbgfont.xb` → 8,464B GIM(`MIG.00.1PSP`), `vtr.xb` → 144B SGXD,
`item_ca00.xb` → 5,328B GIM, `inpane_ca.csv` → 평문 CSV. 모두 바이트 단위로 일치합니다.

### 텍스트 포맷

게임 텍스트는 `.xb` 안의 **`.bin` 리소스**에 있고, 구조는 오프셋표 + 문자열입니다.

```
변형 A:  [u32 count][count × u32 offset][문자열들]     ← 첫 오프셋이 4+count*4
변형 B:  [u32 offset …][문자열들]                       ← 개수 = offsets[0] / 4
```

**인코딩은 UTF-8**입니다(유럽어 메시지 파일은 Latin-1). `.csv` 리소스는 Shift-JIS 와
UTF-8 이 섞여 있습니다.

확인된 텍스트 리소스:

| 리소스 | 항목 | 내용 |
|---|---|---|
| `ball.bin` / `club.bin` | 8 / 32 | 볼·클럽 이름 |
| `face.bin` | 21 | 캐릭터 이름 (ユメリ, シン, ミュウ …) |
| `head.bin` / `body.bin` / `etc.bin` | 108 / 153 / 86 | 착용 아이템 이름 |
| `co_item.bin` | 760 | 대화·안내문 (「はい」「いいえ」「何か箱があります…」) |
| `mes_real_rank*.bin` | 124 | 순위표 코멘트 |
| `msg0~3.bin` | 15 × 4 | **영어·프랑스어·독일어·이탈리아어** (온라인 모드용) |
| **`msg0.bin` (yumo/first)** | **601** | **주 UI 메시지** (세이브/로드, 段位, ランク…) |
| `mes_real_entry*.bin` | 78 | 온라인 인사·각오 정형구 |
| `mes_match_*.bin` | 178 | 매치플레이 라운드·스코어·표창 |
| `clng.bin` / `crssel.bin` / `hist.bin` | 62 | 챌린지·코스선택·기록 |

`entry_c%02d.txt` 19개는 코스 식생 데이터라 번역 대상이 아닙니다.

### 폰트 — `ngot14` (matu/real/real_.xb)

| 리소스 | 크기 | 글리프 | 규격 | 내용 |
|---|---|---|---|---|
| `ngot14.ank` | 2,212B | 158 | 8×14, 14B | 반각(ASCII + 반각가나) |
| `ngot14.j0b` | 14,672B | 524 | 16×14, 28B | JIS 비한자(기호·숫자·영문·가나) |
| `ngot14.j1b` | 83,020B | **2,965** | 16×14, 28B | **JIS 제1수준 한자** (亜부터 순서대로) |

`j1b` 글리프 수가 JIS X 0208 제1수준 한자 개수와 **정확히 일치**하고 첫 글자가 「亜」,
마지막이 「腕」이라 색인 규칙이 확정됩니다. 행 단위 빅엔디안 1bpp입니다.

### 한글화 경로

텍스트는 UTF-8, 폰트는 JIS 색인이므로 렌더러가 UTF-8 → JIS 변환을 합니다. 따라서
메가드라이브 작업들과 **같은 수법**이 그대로 통합니다 — 원본이 쓰지 않는 한자 글리프
자리에 한글 비트맵을 심고, 번역문에는 그 한자를 씁니다. 2,965칸이라 한글 음절 수요에
충분합니다. 14×14 는 12×12 보다 여유가 있어 판독성도 유리합니다.

**슬롯 예산 (실측)** — 추출한 4,398줄에 등장하는 한자는 761종, j1b 슬롯 754칸 사용 →
**여유 2,211칸**입니다. 상용 한글 2,350자 전체를 넣기에는 139칸 모자라지만, 실제로
필요한 것은 번역문에 쓰이는 음절뿐이라 **빈도순 배정으로 충분합니다**. 추가로
번역으로 덮이는 자리의 한자는 슬롯을 회수할 수 있고(트레이지아에서 쓴 방식),
`j0b`(524칸)에도 미사용 영역이 있습니다.

⚠ 메가드라이브에서 이 산정을 잘못해 상용 한자를 덮은 사고가 있었으니, 실사용 한자
집합은 반드시 추출 텍스트 전체로 계산해야 합니다.

### 리소스 위치 — 엔트리가 직접 알려준다

엔트리의 **하위 28비트 × 4 가 그 리소스의 청크 절대 오프셋**입니다.
`dbgfont` `0x10×4=0x40`, `item_ca00` `0x12×4=0x48`, `dlg` `0x21×4=0x84`,
`cmn0` `0x2bd×4=0xaf4` — 모두 데이터 시작 위치와 일치합니다.

이걸 모르고 청크 폭을 누적해 따라가려 해서 대형 파일에서 계속 어긋났습니다
(`history.xb` 24개 중 2개만 나오던 것이 23개로, `ResultRanking.xb` 10 → 22로 회복).
리소스 하나가 실패해도 다음 리소스 위치를 알기 때문에 그냥 넘어갈 수 있습니다.

### ⚠ 이 게임은 PSP 시스템 폰트(PGF)로 텍스트를 그린다

처음에는 `ngot14` 비트맵 폰트의 안 쓰는 한자 칸에 한글을 심는 메가드라이브식 수법을 썼는데
**인게임에 아무것도 반영되지 않았습니다.** 원인이 둘이었습니다.

1. **`ngot14` 폰트는 쓰이지 않습니다.** 그 폰트가 든 `matu/real/real_.xb` 를 코드가 참조하지
   않습니다(실사용은 `matu/real/real.xb`, 거기엔 폰트가 없음) — 개발 잔재입니다.
   게임은 `sceLibFont` 로 **시스템 폰트를 인덱스로 열어** 글리프를 받습니다.
   임포트가 `NewLib/Open/GetFontInfo/GetCharInfo/GetCharGlyphImage/Close/DoneLib` 7개뿐입니다.

   ```
   0x08945990  addu a1,zero,zero   ; 폰트 인덱스 = 0 (jpn0.pgf)
   0x08945998  jal  sceFontOpen
   ```

2. **고친 파일이 로드되는 파일이 아니었습니다.** `msg0.bin` 은 `first.xb`/`first0.xb`/`first3.xb`
   세 팩에 있고, 코드에는 `yumo/first/first%d.xb` 서식만 있습니다. `first1.xb`·`first2.xb` 가
   없어 언어 인덱스에 파일이 없으면 폴백하는 구조로 보여, **세 팩을 모두 같게** 넣습니다.

**해법**: 번역문은 **한글 UTF-8 그대로** 쓰고(치환 없음), 시스템 폰트 인덱스를 `kr0.pgf`(17)로
바꾸는 **4바이트 코드 패치**를 넣습니다. 코드는 디스크에 이미 있는 **평문 ELF `BOOT.BIN`** 을
고쳐 `EBOOT.BIN`(원래 `~PSP` 암호화본) 자리에 덮어씁니다 — CFW·PPSSPP 는 평문 ELF를 실행합니다.

⚠ 폰트가 한국어 PGF로 바뀌므로 **번역하지 않은 일본어는 한자 글리프가 없어 `__` 로 보입니다.**
전량 번역이 전제인 방식입니다.

### 빌드 파이프라인

`python tools/build.py` 하나로 원본 ISO → 한글 ISO 를 만듭니다.

1. 평문 ELF(`BOOT.BIN`)의 `sceFontOpen` 인덱스를 `kr0.pgf`(17)로 바꿔 `EBOOT.BIN` 자리에 넣는다
2. `script/ko.json`(`팩::리소스::인덱스` → 번역문)의 한글을 **UTF-8 그대로** `.bin` 에 쓴다
3. `.xb` 를 다시 패킹한다 — **손대지 않은 리소스는 원본 청크를 그대로 복사**한다
   (전부 다시 압축하면 원본 허프만+LZ보다 커진다)
4. 파일이 섹터 용량 안에 들어가면 제자리에, 넘치면 **미사용 섹터로 옮기고** 디렉터리
   레코드의 LBA·크기를 고친다 — ISO 재빌드가 필요 없다
5. **`mgp.ufl` 의 LBA·크기를 갱신한다** — 게임이 파일을 찾는 실제 기준이라 이걸 빼면
   옮긴 파일은 반영되지 않는다 (아래 참고)

**길이 제한이 없습니다.** `.bin` 은 오프셋표라 문자열을 자유롭게 늘릴 수 있고 `.xb` 도
통째로 다시 만들 수 있어서, 메가드라이브 작업들처럼 바이트를 아껴 쓸 필요가 없습니다.

#### 코덱 판별

⚠ 스트림 첫 바이트로 LZ/허프만을 가르면 안 됩니다. 허프만 표의 `max_len` 이 4의 배수면
`(b & 3) == 0` 이라 LZ 로 오판합니다(`first0.xb::cmstr0.bin` 의 표가 `0x08` 이라 실제로
걸려 그 리소스가 통째로 추출 실패했습니다). **엔트리 플래그**(0=허프만 / 2=LZ)를 우선 쓰고
실패 시에만 추정으로 되돌아갑니다.

⚠ 2단 체인 판정도 `len(out) != final` 로 걸면 안 됩니다 — 바깥 단계 출력이 최종 크기와
우연히 같은 경우가 있습니다(`cmstr0.bin`: 341 == 341).

#### 압축기

해제기 규격에서 역산했습니다. 리터럴 런 `t=((n-1)<<2)` (n≤64), 2바이트 매치
`v=(dist<<4)|((len-3)<<1)|1` (len 3~10), 3바이트 매치 `v=(dist<<12)|((len-3)<<2)|2`
(len 3~1026). 창은 12비트라 **4095바이트**입니다. 추출한 전 파일에서 라운드트립을
확인했고, 압축률은 원본(허프만+LZ 2단) 대비 1.0~1.1배입니다.

#### ⚠ 이 게임은 파일을 `mgp.ufl` 로 찾는다 — ISO 디렉터리가 아니다

실행 파일이 런타임에 `disc0:/PSP_GAME/USRDIR/mgp.ufl` 을 열고, 거기 적힌 **LBA로 디스크를
직접 읽습니다**. 그래서 파일을 옮기고 ISO9660 디렉터리 레코드만 고치면 아무 효과가 없습니다.
게다가 옮길 때 원래 자리는 지우지 않으므로 **원본이 멀쩡히 남아 있어**, 손상 없이
말끔한 일본어가 그대로 나옵니다. 원인을 찾기 아주 어려운 증상입니다.

```
mgp.ufl : mainmenu.xb → LBA 395776, 1,260,180B     ← 게임이 읽는 곳
실제    : mainmenu.xb → LBA   4434, 1,269,984B     ← 옮겨 놓은 곳
```

메뉴 화면 문구가 전부 `mainmenu.xb` 한 파일에 있어서 **그 화면만 통째로 일본어**가 되고,
제자리에 쓴 `first0.xb`(아래 안내문)만 한글로 남는 식으로 나타납니다.

**크기 필드도 같이 고쳐야 합니다.** 파일이 커졌는데 `mgp.ufl` 의 크기가 원본 그대로면
뒤가 잘려 읽힙니다.

#### ⚠ 파일 몫은 자기 크기가 아니라 다음 16섹터 경계까지다

이 이미지는 파일 시작 LBA가 전부 **16섹터 배수**라 파일마다 정렬 여백이 있습니다.
자기 크기만 올림해서 용량을 재면 들어갈 파일도 자리가 없다고 판단해 옮기게 되고,
그러면 위의 `mgp.ufl` 함정에 그대로 걸립니다.

```
mainmenu.xb  크기 1,260,180B = 616섹터   ← 자기 크기만 재면 여기까지
             배정      624섹터 = 1,277,952B   ← 실제 몫 (다음 파일 LBA 396400)
```

새 파일 1,269,984B 는 **제자리에 들어갑니다**. 미사용 섹터 할당기도 이 여백을 다른
파일에 내주지 않도록 같은 규칙으로 맞춰야 합니다.

#### ISO 여유 공간

이 이미지에는 **미사용 섹터가 133.9MB**(LBA 14940에 40,180섹터 연속) 있습니다.
커진 파일은 그쪽으로 옮깁니다. 폰트 팩(`real_.xb`)은 440,000 → 444,632B 가 되어
LBA 4434 로 이동했습니다.

⚠ 디렉터리 레코드의 LBA·크기는 **both-endian**(LE+BE)이라 4곳을 모두 고쳐야 합니다.

### 타이틀 화면 그래픽 (GIM 텍스처)

메뉴 문구 일부는 텍스트가 아니라 **GIM 텍스처**입니다. `yumo/title/title.xb` 안에 있습니다.

| 리소스 | 크기 | 내용 | 처리 |
|---|---|---|---|
| `open_choise.gim` | 256×64 | 「はじめから」「つづきから」 | 「처음부터」「이어하기」 |
| `open_MGP.gim` | 512×256 | 「みんなの GOLF ポータブル 2」 로고 | 「모두의 GOLF 포터블 2」 |

**GIM 포맷** — `MIG.00.1PSP` 뒤에 16바이트 헤더의 청크 트리(2=root, 3=picture,
4=image, 5=palette). 이미지 헤더에 format/pixel_order/width/height/bpp 가 있고,
둘 다 **INDEX8 + 256색 팔레트**입니다.

⚠ `pixel_order == 1` 이면 **스위즐 배열**입니다 — 16바이트 × 8행 블록으로 섞여 있어
그대로 읽으면 그림이 조각납니다. 읽고 쓸 때 모두 풀고/되감아야 합니다.

⚠ 색은 **팔레트에 이미 있는 값만** 씁니다(최근접 인덱스 매핑). 팔레트를 건드리지 않으므로
다른 리소스와 공유되는 경우에도 안전합니다.

처리 방식:
- 「はじめから」류는 원본에서 **행별 그라데이션을 뽑아** 같은 색으로 다시 칠하고
  진회색(22,22,22) 2px 외곽선을 두릅니다. 흰 테두리처럼 보이는 건 그라데이션 윗부분입니다.
- 로고의 「みんなの」는 노랑(255,222,2) + 진회색(42,42,42) 5px 외곽선.
  「GOLF」와 「2」는 그대로 둡니다(영문·숫자라 번역 불필요하고 로고의 정체성).
- 「ポータブル」의 흰 공 배지 5개는 한글 3자에 맞춰 **3개로 줄여 가운데 정렬**합니다.
  ⚠ 원본 배지를 복사하면 위쪽 GOLF 픽셀이 섞여 들어오므로 **절차적으로 다시 그립니다**
  (링 반지름 22 / 공 17, 중심 y=193, 간격 48).
- 서체는 **휴먼매직체**(원본의 둥근 고딕에 가깝습니다).

⚠ **크기는 폭이 아니라 「자당 크기」에 맞춥니다.** 원본 폭에 맞춰 넣으면 글자 수가 줄어든
만큼 한 글자가 커져 어색해집니다.

| 문구 | 원본 | 한글 |
|---|---|---|
| 「みんなの」→「모두의」 | 4자 241px (자당 60px) | 3자 **180px**, GOLF 왼쪽 끝에 맞춰 왼쪽 정렬 |
| 「はじめから」→「처음부터」 | 5자 116px (자당 23px) | 4자 **96px** |
| 배지 안 글자 | — | 19px (원 크기는 원본 유지, 여백 확보) |

「GOLF」와 「2」를 남기고 「모두의」를 왼쪽 정렬하는 구성은 **소니의 공식 한국어 로고**와 같습니다.

#### 지우는 범위와 배지 그리기 — 실측이 필요한 부분

| 항목 | 실측 | 안 지키면 |
|---|---|---|
| 「みんなの」 아래끝 | y=104 가 픽셀 14개뿐인 **빈 행**(y103=일본어 밑동, y105=GOLF 윗 외곽선) | 덜 지우면 「모두의」와 GOLF 사이에 옛 글자 밑동이 점선처럼 남는다 |
| 배지 지우기 | GOLF 글자색은 y=168 에서 끝나고 배지는 y=171 부터 | 사각형으로 지우면 **GOLF 아랫단이 일자로 잘린다**. 원본 원판 5개만 지울 것 |
| 링 두께 | 중심행에서 원 x70~112(외반지름 21), 흰 공은 x74 부터(내반지름 18) → **3px** | 5px 로 그리면 원본보다 두껍다 |
| 배지 안 글자 | 얇은 서체(맑은 고딕) 18px | 휴먼매직체는 획이 두꺼워 「블」 같은 글자가 뭉갠다 |
| 원 가장자리 | 경계 1px 알파 혼합 | 하드 엣지로 그리면 링이 톱니처럼 보인다 |
| 공 음영 | 좌상단 흰색 유지, 우하단만 (156,154,155) 로 대각 음영 | 전체 그라데이션을 주면 공이 칙칙해진다 |

### 메인 메뉴 화면 그래픽

메인 메뉴도 문구가 전부 텍스처입니다. `yumo/mainmenu/mainmenu.xb` 안에 있습니다.

| 리소스 | 크기 | 내용 | 처리 |
|---|---|---|---|
| `toppage_01/02.gim` | 512×512 | 버튼 아이콘 그림 | 글자가 없어 **손대지 않음** |
| `toppage_03.gim` | 512×512 | 버튼 문구 19개 × **3벌** | 한글화 |
| `title_top.gim` | 256×256 | 화면 상단 띠 5종 | 한글화 |

**버튼 문구 — 두 벌이 아니라 세 벌입니다.**

| 열 | x 범위 | 폭 | 내용 |
|---|---|---|---|
| 0 | 2~117 | 116 | 큰 라벨, 흰 채움 + 색 외곽선 (평소 상태) |
| 1 | 121~238 | 118 | 같은 글자의 **흰 실루엣** (커서가 올라간 상태) |
| 2 | 246~322 | 77 | 작은 라벨, 흰 채움 + 색 외곽선 |

세 벌 모두 자기 열 안에서 가운데 정렬이고 색은 항목마다 다릅니다.

⚠ **큰 라벨을 `x 0~224` 한 덩어리로 보면 안 됩니다.** 그렇게 하면 글자가 열 0과 열 1
사이 빈틈(x≈119)에 놓이고, 게임이 쓰는 UV 창을 벗어나 **텍스처가 반대편으로 감깁니다**.
증상이 특이해서 원인을 찾기 어려웠습니다 — 평소엔 앞글자가 잘려 「혼자서 GOLF」가
「자서 GOLF」로 보이고, 커서를 올리면 좌우가 뒤바뀐 채 벌어져 「갈아입기」가
「입기　갈아」로 보입니다. 열마다 **원본 잉크 상자를 실측해 그 안에** 넣어야 합니다.

⚠ 글자를 **폭 기준**으로 그리면 「VTR」처럼 짧은 항목이 거대해지고 「세이브/로드/삭제」처럼
긴 항목이 찌부러집니다. 각 칸의 **높이에 맞춰** 그리고 폭이 넘치면 가로세로 같은 비율로
줄여야 19개가 고르게 나옵니다.

⚠ 흰 실루엣(열 1)의 외곽선은 실측하면 3px 이지만 **2px 로 줄여야** 합니다. 가나는 속공간이
넓어 괜찮지만 한글은 「ㅇ·ㅎ」의 구멍이 메워져 덩어리가 됩니다.

#### 가장자리 처리

원본은 글자 가장자리를 **반투명·중간색**으로 부드럽게 처리합니다(팔레트에 외곽선색의
알파 단계와 흰색과의 혼합색이 들어 있습니다). 이진 마스크로 그리면 테두리가 계단처럼
거칠어집니다. 그래서 글자를 **0~255 커버리지**로 렌더하고, 외곽선은 그 커버리지를
원판으로 **최대값 팽창**시켜 만듭니다 — 바깥 가장자리까지 부드러움이 이어집니다.

**상단 띠** — 32px짜리 띠 5개이고, 왼쪽은 진한 색에서 오른쪽 흰색으로 빠지는 가로
그라데이션 위에 **흰 글자 + 1px 진한 외곽선**이 왼쪽 정렬(x≈10)로 얹혀 있습니다.
글자는 띠 높이를 거의 꽉 채웁니다. 이 크기(15px)에서는 휴먼매직체가 뭉개져
**맑은고딕 Bold** 를 씁니다.

| 띠 | 문구 |
|---|---|
| y 0 | 「메인 메뉴」 |
| y 32 | 「혼자서 GOLF」 |
| y 64 | 「데이터」 |
| y 96 | 「세이브/로드/삭제」 |
| y 128 | 「다같이 GOLF」 |

#### 옛 글자를 지우는 법 — 여기서 세 번 틀렸다

| 시도 | 결과 |
|---|---|
| 흰색·진한색 화소만 골라 지우기 | 안티에일리어싱 중간톤이 남아 **옛 가나가 유령처럼** 비친다 |
| 글자 바로 윗행을 복사해 채우기 | 그 행에 이미 외곽선이 걸려 있어 **어두운 블록**이 생긴다 |
| 열마다 최빈색을 배경으로 삼기 | 세로획이 긴 열은 **흰 글자가 최빈색**이라 흰 막대가 남는다 |
| 오른쪽 끝에서 배경색을 추적 | 텍스처 오른쪽 끝이 투명이라 **띠 전체가 흰색**으로 물든다 |

실측해 보니 띠 배경은 **열마다 완전히 균일**(세로 변화 0)하고, 장식선만 띠시작 +2/+3 과
+28/+29 에 있습니다. 그래서 **띠시작 +4 행을 통째로 복사**하면 완벽하게 지워집니다.
그 행이 깨끗한지는 「가로로 이웃 화소와 60 이상 튀는 개수」로 자동 판정해 후보 4개 중
가장 매끄러운 행을 고릅니다 — 「세이브/로드/삭제」 띠는 +5 행에 옛 글자 삐침이 걸려 있어
그대로 쓰면 그 화소가 세로로 복제돼 **막대기 잔상**이 됩니다.

### 패치 배포 방향

텍스트가 `.xb` 데이터에만 있으면 **코드를 건드리지 않아** EBOOT 재서명 문제가 없습니다.
`isolib.write()` 는 같은 크기 in-place 교체만 허용하므로 ISO 크기·LBA가 바뀌지 않습니다.
크기가 늘어나야 하면 `mgp.ufl` 기준으로 ISO를 재빌드합니다.
